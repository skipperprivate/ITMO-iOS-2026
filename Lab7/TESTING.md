# Тестирование MiniTwitter

В проект добавлены два тестовых target: `MiniTwitterTests` на Swift Testing и
`MiniTwitterUITests` на XCTest. Общая схема `MiniTwitter` включает оба target.

## Запуск в Xcode

1. Открыть `MiniTwitter.xcodeproj`.
2. Выбрать схему `MiniTwitter` и симулятор iPhone с iOS 26 или новее.
3. Нажать `⌘U` (Product → Test) для запуска всех четырёх тестов.
4. Открыть Test Navigator сочетанием `⌘6`, чтобы посмотреть результаты.
   Отдельный тест можно запустить кнопкой рядом с его названием или в редакторе.

Не нужно вручную добавлять аргументы запуска в схему: UI-тесты передают их сами.
Обычный запуск через `⌘R` использует реальный сервер и постоянное хранилище.
Видимое имя приложения изменено на MiniTwitter. Системный идентификатор
`fkirll.Lab3` оставлен прежним, чтобы обновление приложения сохранило существующую
базу SwiftData и настройки UserDefaults.

## Unit-тесты — Swift Testing

Файл: `MiniTwitterTests/TwitterAPIClientTests.swift`.

### 1. fetchPostsDecodesResponse

Проверяет настоящий `TwitterAPIClient`, которому передаётся отдельная
`URLSession` с тестовым `URLProtocol`. Подмена принимает только GET по пути
`/api/posts` с параметрами `page=2`, `pageSize=1` и заголовком
`Accept: application/json`. Неправильный запрос завершится ошибкой и провалит тест.

Подмена возвращает фиксированный JSON. Через `#expect` проверяются параметры
страницы, наличие следующей страницы, число записей, UUID, никнейм, имя автора,
текст, дата и число лайков. `#require` извлекает первый пост и останавливает тест,
если его нет.

### 2. fetchPostsReportsServerError

Подмена возвращает HTTP 500 и тело, которое не является JSON. Проверка
`#expect(throws: TwitterAPIError.http(500))` подтверждает точную ошибку. Если клиент
проигнорирует статус и попробует разобрать тело, получится другая ошибка и тест
не пройдёт. Если клиент вообще не выбросит ошибку, тест также не пройдёт.

Оба теста используют `@Test` и `async/await`, не наследуются от `XCTestCase` и не
обращаются к реальному серверу. У каждого своя сессия; у подмены нет общего
изменяемого состояния, поэтому тесты не зависят от порядка выполнения.

## UI-тесты — XCTest

Файл: `MiniTwitterUITests/TweetsUITests.swift`.

### 1. testCreateLocalTweetFromHome

Запускает приложение, переходит с главного экрана в ленту и открывает редактор.
Проверяет, что пустой текст нельзя сохранить. Вводит текст, сохраняет и проверяет,
что редактор закрылся, а новый текст и подпись «Локальный твит» появились в ленте.

### 2. testFavoritesFilterAndRemoval

Проверяет наличие двух тестовых записей и отсутствие закладки у первой.
Добавляет первую в избранное, включает фильтр и проверяет, что осталась только
выбранная запись. Убирает закладку и проверяет пустое состояние. Возвращается к
фильтру «Все» и проверяет, что обе записи остались, а закладка снята.

UI-тесты наследуются от `XCTestCase`, управляют приложением через `XCUIApplication`
и используют `XCTAssert`. Элементы находятся по `accessibilityIdentifier`, для
сегментов фильтра используются русские подписи при явно заданном языке запуска.
Ожидания проверяют появление клавиатуры, полный введённый текст, появление,
исчезновение, доступность для нажатия и значение элементов;
фиксированных пауз в тестах нет.

## Изоляция данных

UI-тесты запускают приложение с `--ui-testing`. В Debug этот аргумент включает
`MockTweetsAPI`, SwiftData в памяти и отдельный UserDefaults suite `MiniTwitter.UITests`,
который очищается перед каждым тестовым запуском. Каждый тест получает чистую
ленту, не использует интернет и не отправляет реальные лайки. Обычная база и
стандартный UserDefaults не очищаются. В Release аргумент не включает тестовый режим.

Тесты UI запускаются последовательно в общей схеме. База в памяти не проверяет
сохранность данных после завершения процесса — это проверяется отдельно старым
скриптом `Tests/run-concurrency-checks.sh`.

## Запуск из терминала

Из папки проекта, если установлен симулятор с именем `iPhone 17`:

```sh
xcodebuild -project MiniTwitter.xcodeproj -scheme MiniTwitter \
  -destination 'platform=iOS Simulator,name=iPhone 17' test
```

Добавить `-only-testing:MiniTwitterTests` для запуска только unit-тестов или
`-only-testing:MiniTwitterUITests` для запуска только UI-тестов.

Существующие дополнительные проверки миграции, CRUD, сети и конкурентности:

```sh
bash Tests/run-concurrency-checks.sh
```

Это отдельные программные проверки, не замена четырём тестам на требуемых фреймворках.

## Результат проверки

Проверки выполняются на симуляторе iPhone 17 с iOS 26.0.1. При повторных прогонах
обнаружено нестабильное нажатие «Сохранить» в UI-тесте. Добавлены явные ожидания
клавиатуры, полного введённого текста и готовности кнопки к нажатию. После этого
22 октября 2026 года выполнены три полных контрольных прогона: все четыре теста
прошли в каждом прогоне (12 успешных выполнений, 0 ошибок, 0 пропусков).
Дополнительный скрипт миграции и конкурентности прошёл. Release-сборка
проверена отдельно и собирается без предупреждения о недостижимой тестовой ветке.

29 октября 2026 года после переименования проекта в MiniTwitter сборки Debug и
Release и все четыре теста Xcode прошли повторно. Дополнительный скрипт проверил
чтение базы, созданной прежним модулем `Lab3`, новым модулем `MiniTwitter`, а также
сохранность данных между запусками.

## Коротко для защиты

Unit-тест проверяет отдельный компонент: сетевой клиент получает контролируемый
ответ и должен правильно разобрать данные или вернуть ошибку. UI-тест проверяет
сценарий глазами пользователя: нажатия, ввод текста и результат на экране.
Подменяется только внешний источник данных; интерфейс, ViewModel и локальный
репозиторий в UI-тестах остаются настоящими.

Документация: [Swift Testing](https://developer.apple.com/documentation/testing),
[XCTest](https://developer.apple.com/documentation/xctest).
