# Swift Concurrency в MiniTwitter

Сетевые запросы выполняются в `TwitterAPIClient` через `URLSession` и `async/await`.
Метод отправки и декодирования помечен `@concurrent`, поэтому обработка JSON
выполняется вне `MainActor`. `MockTweetsAPI` используется только в Preview.

`TweetCacheRepository` — `@ModelActor`, владеющий собственным `ModelContext`.
`TweetRepositoryProvider` создаёт один репозиторий через `Task.detached` и возвращает
его при повторных переходах в ленту. `BackgroundModelExecutor` выполняет задачи
актора в последовательной фоновой очереди; обращения к базе сериализованы.

Между сетевым клиентом, репозиторием и ViewModel передаются структуры `Sendable`.
SwiftData-модели остаются внутри репозитория. `TweetsViewModel` изолирована
`MainActor`, обновляет интерфейс после `await` и управляет состояниями загрузки,
обновления и сохранения.

Во время GET можно работать с локальным кэшем. Объединение данных сохраняет локальные
отметки и не уменьшает подтверждённый счётчик лайков при получении более старого ответа.
Снимки репозитория содержат ревизию: ViewModel не применяет устаревший снимок,
если результат другой операции уже был показан.

Загрузка привязана к `.task`; задачи кнопок повторной загрузки и пагинации отменяются
при уходе с экрана. Отмена не показывается как ошибка. Запись из формы ожидает
результат, блокирует повторное сохранение и закрывает форму только при успехе.

Проверки запускаются командой:

```sh
bash Tests/run-concurrency-checks.sh
```

Они проверяют параллельное объединение страниц, 12 конкурентных записей, отмену,
повтор загрузки, CRUD и сохранение данных между процессами. В отладочной сборке
`assert` проверяет выполнение операций репозитория вне главного потока.
Сетевые сценарии описаны в [NETWORKING.md](NETWORKING.md).
