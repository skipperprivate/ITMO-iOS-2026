ДВА СЕТЕВЫХ СЦЕНАРИЯ
1. GET https://dummyjson.com/posts?limit=30
   При открытии или обновлении ленты загружаются 30 публикаций.
   JSONDecoder разбирает массив posts: id, title, body, userId, tags.
   В ленте отображаются заголовок, полный текст, автор и категория из API.
   Это содержательные учебные записи на английском, не актуальные новости.
   Нет подстановки локальных фиктивных записей при ошибке сервера.
2. POST https://dummyjson.com/posts/add
   Открыть плюс, заполнить заголовок и текст, нажать
   «Отправить на учебный сервер».
   JSONEncoder создаёт тело {title, body, userId: 1}.
   Content-Type: application/json. Сервер возвращает 201 и JSON новой записи.
   Приложение декодирует ответ, сохраняет именно возвращённые title/body,
   показывает ID сервера и добавляет локальную копию в ленту.
   Источник и категория формы — локальные поля, в POST не отправляются.
   «Сохранить локально» выполняет прежнее сохранение без сетевого запроса.

ОГРАНИЧЕНИЕ УЧЕБНОГО API
DummyJSON имитирует создание: HTTP-запрос и ответ реальные, но сервер не
сохраняет новую запись постоянно. Следующий GET не вернёт созданный POST.
Это явно написано в редакторе и подтверждении. Локальная запись сохраняется
в SwiftData и остаётся после обновления ленты и перезапуска приложения.
ID нового POST может повторяться, поэтому локальное сохранение использует
UUID операции. Нельзя называть этот режим полноценной серверной публикацией.

АРХИТЕКТУРА
NewsApp создаёт сетевой клиент и репозиторий, передаёт их вниз по зависимостям.
GET: NewsFeedView → NewsFeedViewModel → NewsFetching → NewsAPIClient.
POST: NewsEditorView → NewsEditorViewModel → NewsPublishing → NewsAPIClient.
NewsAPIClient → HTTPTransport → URLSessionTransport → URLSession.
JSON → приватные Decodable DTO → Sendable-модели RemoteArticle/CreatedPost.
ViewModel → NewsRepository → SwiftData Item → отображение в SwiftUI.

View отвечает за отображение, ввод и запуск действия ViewModel.
В Views нет URLRequest, URLSession, JSONEncoder/JSONDecoder и адресов API.
ViewModel управляет загрузкой, ошибками и сохранением, но не собирает HTTP.
Сетевой сервис отвечает за запрос, HTTP-статус, JSON и проверку содержимого.
Репозиторий занимается только локальными данными, не делает сетевые запросы.

ОБРАБОТКА ОШИБОК И ДАННЫХ
— Тайм-аут запроса 20 секунд; проверяются HTTP 2xx до разбора JSON.
— Отдельные сообщения для отсутствия сети, тайм-аута, HTTP и неверного JSON.
— Пустой список отличим от поломанного ответа. Пустые title/body и неверный
  ID в ответе не маскируются под успешную загрузку.
— При сбое GET кеш остаётся; при пустом кеше интерфейс сообщает, что данных нет.
— Кнопка «Повторить загрузку» и pull-to-refresh повторяют GET.
— Ошибка сохранения не выдаётся за ошибку сети и не маскируется успехом.
— Ошибка POST оставляет введённый текст в редакторе.
— Повторная отправка блокируется на время запроса; поля формы также блокируются.
— После успешного POST и ошибки диска повторяется только локальное сохранение,
  без второго POST. Это действует, пока открыт редактор; долговечной очереди нет.
— Автоматических повторов POST нет. При сетевом тайм-ауте неизвестно, успел ли
  сервер принять запрос; полноценный backend потребовал бы idempotency key.
— Отмена Task/URLSession не показывается как сетевая ошибка.
— merge обновляет по remoteID вида dummyjson:ID, сохраняя локальные публикации.
— Удаление сетевой записи локальное: следующий GET может вернуть её снова.
— Дата у DummyJSON отсутствует: показывается «Загружено», это дата первого
  сохранения. У собственных публикаций показывается дата создания.
— Сетевые записи доступны для чтения; свои записи редактируются локально.
  После локальной правки отметка прежнего ответа POST снимается.

МНОГОПОТОЧНОСТЬ
URLSession приостанавливает async-задачу во время I/O, не блокируя UI.
JSON декодируется на actor сетевого сервиса; статистика — на своём actor.
Actors не гарантируют постоянного отдельного потока. CPU-поиск выполняется
в Task.detached с передачей отмены. ModelContext и Item используются на
MainActor; между actors передаются Sendable-значения, не SwiftData-объекты.

ПОКАЗ ПРЕПОДАВАТЕЛЮ
1. Запуск с сетью: дождаться GET и открыть запись с полным текстом.
2. Обновить ленту: одинаковые ID не создают дубли.
3. Плюс → заполнить заголовок/текст → отправить на учебный сервер.
4. Показать подтверждённый ID и новую запись в ленте после закрытия редактора.
5. Отключить сеть: GET показывает ошибку и сохранённую ленту; POST показывает
   ошибку и сохраняет ввод. Можно сохранить запись локально без отправки.
6. Показать create/fetchArticles в NewsAPIClient и методы submit/refresh
   в ViewModel. Отдельно показать сохранение результата в NewsRepository.
7. Повторный запуск офлайн должен открыть кеш; проверить это в симуляторе.

ПРОВЕРКИ И ИХ ГРАНИЦЫ
Реальный GET выполнен: 30 записей, у всех непустые заголовки и тексты.
Реальный POST выполнен: HTTP 201, ID 252, сервер вернул отправленный текст.
Сетевой слой, поиск, статистика и соответствующие ViewModel компилируются
Swift 6.1.2 со strict-concurrency=complete. Отдельной исполняемой проверкой
в рабочей папке проверены GET/POST, JSON, HTTP-ошибка, отсутствие сети,
пустой ввод, пустой список, поиск и статистика. Это не новые XCTest проекта.
Полная сборка приложения и визуальный запуск не подтверждены: на машине
нет Xcode/iOS Simulator; в Command Line Tools отсутствует SwiftDataMacros.
SwiftData-сохранение, миграцию и интерфейс нужно прогнать в Xcode.
